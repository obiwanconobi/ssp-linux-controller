# StompStation 0.6.0 plan

Changes requested after the 0.5.0 release, with the findings needed to start
implementation tomorrow. The Parametric EQ GUI should reuse the Global EQ graph,
and preset export/import is now specified around the device's actual list and
chunk protocol rather than guesswork.

The reference export is `docs/Brave.zip`, exported from the official
StompStation PRO app on firmware 2.5.3. It is a local reference archive and is
intentionally **not committed** because it contains third-party NAM/PNAM/IR
captures. Keep it locally for implementation and testing; do not publish it.

## What was confirmed on hardware (2.5.3)

These paths and shapes were read from the live device and from `Brave.zip`:

- `root\settings\input\gain1` and `gain2` are floats, **−15.0 … +15.0 dB**,
  step `0.1`.
- `root\settings\input\_connected1` and `_connected2` are read-only enums with
  options `NO` / `YES`.
- `root\app\output\pst\level` is the **Preset Level** control: float,
  **−20.0 … +20.0 dB**, step `0.1`, default `0.0`.
- The in-chain Parametric EQ is `root\app\parametric_eq`, with four bands under
  `eq_par`: `band_0..3` (−15 … +15 dB), `freq_0..3` (50 … 20000 Hz),
  `q_0..3` (0.1 … 10), `type_0..3`, and a block `on_off`.
- `root\app\eq` / `root\app\eq2` are the separate 8-band **Graphic EQ** blocks.
  Do not reuse those paths for the Parametric EQ GUI.
- `root\presets` is a `list` with `size: 32768`, `chunk: 1024`, and
  `item_type: pst_pst`; each preset is a 32 KiB `.pst` payload.
- `dread <listPath>:{"index":N,"chunk":C}` starts at **chunk 1** for list
  payloads. Chunk 0 returns an empty frame. There is no final `chunk:-1`
  response for these lists; request chunks until the declared size is reached.
- For a NAM/PNAM list the first response includes `size` (the gzip payload
  size); the downloaded bytes are gzip-compressed and must be decompressed.
  For IR/WAV lists there is no `size` in the response; use the list node's
  `size`/`chunk` values. Live 2.5.3 verification (2026-11-23) showed the payload
  is **8192 bytes of raw little-endian `f32` samples**, not a WAV file. Wrap it
  in the official 48 kHz mono float WAV header when writing or exporting.
  WAV validation must run after that wrapper, not on the raw device bytes.
- `root\presets` has a `used` map keyed by preset-relevant paths. Example keys:
  - `root\app\amp\model`, `root\app\amp\pmodel`,
    `root\app\amp\nam2\model`, `root\app\amp\nam2\pmodel`
  - `root\app\drive\model`, `root\app\drive\pmodel`
  - `root\app\ir\ir`, `root\app\ir\ir2\ir`

  Each key holds one name per preset slot. Use this map to identify which
  presets reference a capture and to collect export dependencies.
- List rename uses the same chunked name write already used for presets:
  `dwrite <listPath>:{"index":N,"chunk":-1,"value":"<128-byte name as hex>"}`.

## 4. Preset export

The official archive is a zip assembled from the preset list payload plus
referenced capture files. `Brave.zip` contains:

```text
bdinfo.json
preset/Brave.pst
dependencies/root/nam_drive/TTS Corn G2 - S00 T00 V10 - A2.nam
dependencies/root/pnam_drive/TTS Corn G2.pnam
dependencies/root/nam_amp/Match Brave Hi D 2.nam
dependencies/root/ir_list/TJ3 G10S50 2x10 SM545.wav
```

`bdinfo.json` is the manifest:

```json
{
  "applicationName": "StompStation PRO",
  "author": "SONULAB Audio Systems",
  "version": "2.5.3",
  "preset": {
    "name": "Brave",
    "extension": "pst",
    "nodePath": "root\\presets",
    "archivePath": "preset/Brave.pst"
  },
  "dependencies": [
    {
      "name": "Match Brave Hi D 2",
      "extension": "nam",
      "nodePath": "root\\nam_amp",
      "archivePath": "dependencies/root/nam_amp/Match Brave Hi D 2.nam"
    }
  ]
}
```

`Brave.pst` is a 32 KiB file of CRLF-separated lines:

```text
root\app\router:{"value":[...]}
root\app\drive\model:{"value":"..."}
root\app\drive\on_off:{"value":"ON"}
root\app\output\pst\level:{"value":0.000000}
root\app\output\pst\tmp:{"value":120.000000}
```

The trailing NUL bytes pad the file to 32 KiB. It contains only preset paths
under `root\app\...`; global settings such as input gain or tuner state are not
included.

### Export algorithm

1. Read the selected preset slot's `.pst` from `root\presets` using `dread`
   chunks `1..size/chunk` (chunk size is 1024 bytes here). Do not expect a
   `chunk:-1` terminator.
2. Use `root\presets.used` at that preset index to list the exact dependency
   node paths and names.
3. Download each dependency with `dread`:
   - NAM/PNAM: use the response's compressed `size`, collect chunks `1..N`,
     gzip-decompress, and verify the decompressed file is structurally valid.
   - IR/WAV: use the list node's `size`/`chunk` (or chunk count); the payload is
     raw `f32` samples, so wrap it in the official float-WAV header and verify
     the resulting RIFF/WAVE file.
4. Write `bdinfo.json` using the preset name, extension, node path, archive
   path, and one dependency entry per referenced file.
5. Zip the manifest, `.pst`, and dependencies with the same relative paths.
6. Show a save dialog and never overwrite silently.
7. Re-open the zip and verify `bdinfo.json`, preset size/paths, dependency
   names, and dependency sizes before reporting success.

### Decisions and edge cases

- Use the device's stored `.pst` bytes rather than re-serializing UI state; this
  guarantees byte-compatible export.
- Name the archive `<Preset>.zip`; sanitize the filename but preserve the
  preset name in `bdinfo.json`.
- If a dependency name appears in `used` but the file is missing, block export
  and name the missing dependency. Do not silently omit it.
- If two dependencies resolve to the same archive path, block export rather than
  overwrite one.
- Test with an unused blank preset as well as `Brave`; a preset with no
  dependencies should produce a four-entry zip (`bdinfo`, `.pst`, and no
  dependency directory).
- Confirm on hardware that the downloaded `.pst` is byte-identical to the
  official app's `Brave.pst` after removing the archive's filename metadata.

## 5. Preset import

Import the same archive shape. Prefer unpacking client-side over treating the
whole zip as an opaque device bundle, because `dread` on `root\presets` returns
the `.pst` payload rather than a zip.

1. Accept a `.zip` chosen by the user.
2. Reject absolute paths, `..`, and any entry outside `preset/` and
   `dependencies/`.
3. Parse and validate `bdinfo.json`:
   - `applicationName` and format version;
   - preset extension and node path;
   - every `archivePath` exists;
   - every dependency node path is one of the allowed capture lists.
4. Parse the `.pst` for path safety and allowed roots:
   - only `root\app\...` paths;
   - reject actions/settings/global paths;
   - reject duplicate paths and invalid JSON.
5. Show a preflight summary: preset name, target slot, block/chain changes,
   dependencies, and overwrite decisions.
6. Choose an empty target preset slot by default. If the target is occupied,
   require an explicit delete/overwrite confirmation or a new slot.
7. Upload dependencies first through the existing validated model/IR upload
   path. Match existing dependencies by name:
   - reuse an identical existing file;
   - ask before overwriting a different file with the same name;
   - otherwise upload to a free slot and keep the original name.
8. Upload the `.pst` to `root\presets` at the target index using the name chunk
   plus data chunks, mirroring the existing upload ACK logic. Stop on the first
   rejected/wrong-slot ACK.
9. Read back the preset list and the target `.pst`; compare the imported preset
   name and size. Refresh the snapshot and select the imported preset.
10. Do not apply partial state silently. If a dependency succeeds but the `.pst`
    fails, report which dependencies were written and leave a clear retry path.

### Import questions to settle with one hardware run

- Does the preset list `dwrite` need a `chunk:-1` final marker when the payload
  is exactly 32 KiB, or does the target size terminate the upload?
- Does the device validate `bdinfo.json` if we upload dependencies and `.pst`
  ourselves? If not, our client-side validation is the only guard.
- Does uploading a dependency to a used slot update `root\presets.used`
  immediately, or only after the preset is reloaded?
- What does the device do if a dependency upload is cancelled after some chunks?
  Verify the target slot state and retry behaviour.

Test with `Brave.zip`, a no-dependency preset, and a malformed archive before
hardware.

## 6. Library file download

Add download for NAM, PNAM, and WAV/IR entries from the device lists.

- Use `dread` chunks starting at **1**; chunk 0 is empty on 2.5.3.
- For NAM/PNAM, use the first response's `size` as the compressed payload size,
  collect all chunks, gzip-decompress, and verify the model structure.
- For IR/WAV, use the list node's `size`/`chunk` (or the chunk count); the
  payload is 2048 raw `f32` samples. Wrap it in the official 56-byte float-WAV
  header, then verify the RIFF/WAVE header and decoded sample count.
- Show progress and allow cancellation at chunk boundaries.
- Never overwrite an existing local file without a Save As confirmation.
- Handle empty slots, missing lists, and disconnects mid-download.
- Add simulator tests, then a hardware pass for each list type.

This is also useful for export diagnostics and for users who want a local copy
of a capture without the official app.

## 8. Library file rename

Add rename for NAM, PNAM, and IR/WAV entries in the Library.

### Device command

Generalise the existing preset rename implementation:

```text
dwrite <listPath>:{"index":N,"chunk":-1,"value":"<128-byte padded name as hex>"}
```

Then re-read the list and verify the name at `index N`. Use the existing
63-byte/control-character/case-insensitive duplicate validation. Allowed list
paths: `root\nam_amp`, `root\nam_drive`, `root\pnam_list`, `root\pnam_drive`,
`root\ir_list`.

### UI

- Add a rename action to each used Library row, with the current name
  pre-filled.
- Show a confirmation that dependencies may be affected.
- Disable rename for empty slots and names that fail validation.
- On success, refresh the list, preserve the index, and update the current
  preset's model/IR value only if the firmware requires it.
- If the capture is currently used by the open preset, refresh the block and
  verify the model/IR still resolves.

### Does renaming require changing presets?

`root\presets.used` maps preset-relevant node paths to names per preset slot.
Before renaming, inspect it for the old name and present the affected presets.
Then run this hardware investigation on a scratch preset:

1. Create/select a scratch preset that uses a scratch NAM capture.
2. Rename that NAM in Library.
3. Refresh and reload the preset.
4. Check whether `root\app\amp\model` still contains the old name, whether the
   block reports a missing model, and whether `root\presets.used` changed.
5. Repeat for PNAM and IR, and for a capture not used by any preset.

Decision policy:

- If the firmware updates references automatically, allow rename for all
  captures and show the affected preset list as information.
- If it does **not** update references, v0.6.0 should **block rename for used
  captures** and explain which presets use them. Renaming unused captures is
  safe.
- Updating all affected presets (load, rewrite the model/IR node, save, restore
  the previous preset) is a separate follow-up; it is riskier and should not be
  mixed into the first rename release unless the hardware test proves it can be
  done atomically.

Add tests for name validation, readback, duplicate rejection, unused-capture
rename, used-capture blocking, and a hardware pass for each list type.

## Open questions and how to resolve them

| Question | Resolution |
| --- | --- |
| Exact list `dread` termination | Confirmed: chunks start at 1 and run to the declared size; no `-1` terminator on 2.5.3. Verify with a full 32 KiB preset and a partial-size NAM. |
| NAM/PNAM download compression | Confirmed gzip on the first NAM chunk. Decompress and validate before writing. |
| IR download size | Use list `size`/`chunk`; verify the last WAV chunk and header. |
| Preset list upload final marker | Capture `dwrite` ACKs for a `.pst` exactly 32 KiB; decide whether to send a final `chunk:-1` chunk. |
| Dependency reference updates on rename | Run the scratch-preset experiment above; choose the policy accordingly. |
| Export archive ordering | Zip order does not matter for extraction, but write `bdinfo.json` first for readability and compare archive paths, not byte order. |
| Missing dependencies | Block export with the missing name; do not produce an incomplete archive. |
| Occupied target slot on import | Refuse unless the user explicitly deletes or chooses another slot. |
| Gzip metadata | Use a deterministic zip writer and preserve dependency bytes exactly. |
